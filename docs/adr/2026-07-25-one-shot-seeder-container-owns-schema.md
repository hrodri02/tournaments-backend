# A one-shot container owns the schema and seed data

## Status
Accepted — 2026-07-25

## Context
`AppUserConfig` seeds mock users, teams, leagues, games and stats from a
`CommandLineRunner`. Once local development moved to two backend instances
sharing one Postgres database, both instances ran that runner.

Two guards were added in response: a `count() > 0` check, then a
`SEEDER_INSTANCE_ID = "backend-1"` comparison, because `count() > 0` cannot
close the check-then-act race — both instances can observe an empty table
before either commits.

Neither guard addressed the larger problem. `application.properties` sets
`spring.jpa.hibernate.ddl-auto=create-drop`, so *each* instance ran schema DDL
on startup. The second instance to boot dropped and recreated every table,
discarding whatever the first had just committed. Whether seed data survived
depended on which instance finished DDL last.

## Decision
Give schema and seed ownership to a single one-shot Compose service, `db-init`.

It runs the same image as the backends (`tournaments-backend:local`, shared via
the `x-app-image` anchor) with `SPRING_PROFILES_ACTIVE=seed`,
`SPRING_JPA_HIBERNATE_DDL_AUTO=update`, and
`SPRING_MAIN_WEB_APPLICATION_TYPE=none`. It boots Spring, creates the schema,
runs the seeding logic, and exits 0. The backends declare
`depends_on: db-init: condition: service_completed_successfully` and run with
`SPRING_JPA_HIBERNATE_DDL_AUTO=validate`, so they never issue DDL.

`AppUserConfig` is annotated `@Profile("seed")` and the instance-id guard is
deleted. Exactly one process seeds, enforced by container lifecycle rather than
by an identity check inside application code.

Rejected alternative: Flyway migrations, or a `psql` container running `.sql`
files. Both are the better production answer, but the seed data is ~90 players
whose passwords come from `BCryptPasswordEncoder.encode(...)`. Expressing it as
SQL means hardcoding that many bcrypt hashes and hand-maintaining every join
table in parallel with the JPA entities. Reusing the app image keeps the
entities, builders, and encoder as the single definition of the seed data.

## Consequences
- `db-init` must be idempotent, because Compose restarts a dependency whenever a
  service that depends on it is restarted — so `docker compose restart backend-1`
  re-runs the seeder. `SPRING_JPA_HIBERNATE_DDL_AUTO=update` plus the `count() > 0`
  guard makes that re-run a no-op: the schema already exists, the seeder returns
  early, and the data is untouched.

  Neither other `ddl-auto` value works here. `create-drop` drops the schema the
  instant the seeder's JVM exits. `create` was tried first and is worse than it
  looks: restarting one backend made `db-init` issue 26 `drop table` statements
  while the *other* backend was still serving traffic, silently invalidating the
  tokens it had issued.
- Because `update` never drops columns, an entity change can leave schema drift.
  `docker compose down -v` is the clean-slate path, and the backends' `validate`
  catches drift at startup rather than letting it go unnoticed.
- Backends running `validate` will fail fast if the entities and the schema
  `db-init` produced ever diverge. Both are generated by the same Hibernate
  version from the same entities, so they agree by construction.
- Running the app from source no longer seeds by default; that flow needs
  `./mvnw spring-boot:run -Dspring-boot.run.profiles=seed`.
- Integration tests activate `@ActiveProfiles("test")`, so the seeder no longer
  runs during `./mvnw test`. Nothing depended on it: the tests assert against
  relative counts, and the one test referencing a seeded address asserts
  `BadCredentialsException`, which holds whether or not that user exists.
- The Postgres healthcheck now interpolates `${POSTGRES_USER}` / `${POSTGRES_DB}`
  instead of hardcoding them. `db-init` and both backends gate on that
  healthcheck, so a hardcoded user/database that a changed `.env` invalidated
  would have wedged the whole stack.
- Schema creation still happens through Hibernate, just relocated to one
  container. Adopting Flyway remains the natural next step if the schema ever
  needs versioned, reviewable migrations.
